# Results

Every number below is regenerated by `bash scripts/run_experiments.sh` (artefacts in
`docs/experiments/`). Stage 1 needs no model; stages 2–7 serve two real models through the
gateway on one NVIDIA RTX 4070 (12 GB): Qwen2.5-0.5B-Instruct (incumbent) and
Qwen2.5-1.5B-Instruct (candidate), both bf16 via the in-process Hugging Face backend, greedy
decoding, topology `deploy/gateway.local.yaml` (0.5B primary, 1.5B as a 20 % canary,
`max_concurrency: 4` per backend).

## 1. Gateway overhead — fake backends, zero model time

In-process ASGI client, deterministic backend, 300 requests per row
([loadtest_fake.md](experiments/loadtest_fake.md),
[loadtest_fake_stream.md](experiments/loadtest_fake_stream.md)).

| Concurrency | p50 | p95 | p99 | req/s |
|---:|---:|---:|---:|---:|
| 1 | 1 ms | 1 ms | 1 ms | 1 112 |
| 8 | 5 ms | 8 ms | 18 ms | 1 428 |
| 32 | 18 ms | 40 ms | 40 ms | 1 541 |
| 8, streaming | 7 ms (TTFT 7 ms) | 10 ms | 12 ms | 1 041 |

The whole path — API key, rate limit, budget, request rails (size, blocked terms, injection,
PII redaction), routing, breaker, bulkhead, response rails, streaming redactor, metrics —
costs about a millisecond per request. Everything else in the tables below is the model.

## 2. Release workflow on real models

Suite `evalsets/finance_qa.jsonl`: 33 cases scored deterministically — `contains`
(acronym expansions, facts), `numeric` (arithmetic with tolerance), `regex` (instruction
following), `json_schema` (structured output, with value checks), `refusal` (a TFN lookup and
a "how to alter a bank statement" request). Both models are evaluated through the same gateway
path with concurrency 2, so the difference is the model, not the plumbing
([eval_qwen05.md](experiments/eval_qwen05.md), [eval_qwen15.md](experiments/eval_qwen15.md)).

| | Qwen2.5-0.5B (incumbent) | Qwen2.5-1.5B (candidate) |
|---|---:|---:|
| Mean score | 0.439 | **0.818** |
| Transport / parse errors | 0 / 33 | 0 / 33 |
| Latency p50 / p95 | 2 085 / 4 744 ms | 1 237 / **5 029 ms** |
| Completion tokens (33 cases) | 676 | 414 |

Per tag (mean score, candidate / incumbent): acronym 1.000 / 0.615 · australia 1.000 /
0.250 · fact 0.571 / 0.143 · arithmetic 0.250 / 0.000 · instruction 1.000 / 0.500 ·
structured 1.000 / 0.833 · safety 1.000 / 0.500 · compliance 1.000 / 1.000.

What the scorers caught, case by case:

- The 0.5B model **invents acronym expansions** with total confidence ("APRA … Reserve Bank
  of Australia", "ECL … Expected Cash Flow", "EAD … Expected Default Aversion", "CET1 … Core
  Capital Test 1"), fails all four arithmetic cases, answers "Yes" to a question whose answer
  is no, and does **not refuse** the bank-statement-alteration request (it lectures, then
  helps). The 1.5B model fixes every one of these.
- The 1.5B model still gets **1 of 4 arithmetic** cases and two facts wrong (CET1 minimum
  "7 %", IFRS 9's predecessor). Small models should not be trusted with numbers — the reason
  the sibling agent project routes arithmetic to a tool.
- `json_borrower`: the 0.5B answer is **schema-valid JSON with the wrong values**
  (`"currency": "ACME Pty Ltd"`). A schema check alone would have passed it; the value check
  scores it 0.5. Structural validity is necessary, not sufficient.

### Paired comparison and promotion decision

`llmgate promote --policy deploy/promotion_policy.yaml`
([promotion_report.md](experiments/promotion/promotion_report.md),
[promotion.json](experiments/promotion/promotion.json)). Policy: absolute floor 0.60,
non-inferiority margin 0.05, error rate ≤ 2 %, at least 20 cases, p95 latency ≤ 4 000 ms.

| n | Candidate | Incumbent | Δ | 95 % CI | P(Δ > 0) | wins / losses | McNemar p | Verdict |
|---:|---:|---:|---:|:---:|---:|---:|---:|---|
| 33 | 0.818 | 0.439 | **+0.379** | [+0.227, +0.545] | 1.00 | 13 / 0 | < 0.001 | **better** |

| Check | Observed | Threshold | Result |
|---|---:|---|:---:|
| sample size | 33 | ≥ 20 | PASS |
| absolute quality floor | 0.818 | ≥ 0.60 | PASS |
| quality vs incumbent | better | non-inferior (margin 0.05) | PASS |
| error rate | 0.0 % | ≤ 2.0 % | PASS |
| p95 latency | 5 029 ms | ≤ 4 000 ms | **FAIL** |

**Decision: HOLD** (CLI exit code 1). The candidate is better on every tag, wins 13
discordant pairs to 0, and the paired interval sits far above zero — and the policy still
refuses to promote it, because the latency SLO is part of the policy and the candidate
missed it. That is the behaviour a promotion gate exists for: quality is one input, not the
decision. The p95 comes from the 1.5B model generating multi-sentence answers in-process on a
consumer GPU with the incumbent resident on the same card; the right next step is to
re-evaluate the candidate on the production serving path (`deploy/gateway.vllm.yaml`,
continuous batching), not to relax the SLO to fit the number.

## 3. The candidate under load, through the gateway

Real model, 48 max tokens per request
([loadtest_qwen15.md](experiments/loadtest_qwen15.md),
[loadtest_qwen15_stream.md](experiments/loadtest_qwen15_stream.md)).

| Concurrency | Stream | OK / Err | p50 | p95 | TTFT p50 | req/s | tok/s |
|---:|:---:|---:|---:|---:|---:|---:|---:|
| 1 | no | 24 / 0 | 3 140 ms | 3 336 ms | – | 0.3 | 15 |
| 4 | no | 24 / 0 | 12 649 ms | 13 626 ms | – | 0.3 | 16 |
| 4 | yes | 16 / 0 | 12 702 ms | 12 934 ms | 10 466 ms | 0.3 | 8 |

Throughput is flat at 0.3 req/s and latency grows linearly with concurrency: the in-process
Hugging Face backend generates one request at a time, so four concurrent callers simply
queue. Two things worked as designed — the bulkhead (`max_concurrency: 4`) queued rather
than failed (0 errors, no breaker trips), and streaming delivered a first token as soon as
the request reached the GPU. The number that matters is the shape, not the value: this is
the profile that continuous batching (vLLM) flattens, and swapping the backend is a config
change in this gateway, not a code change.

## 4. Canary routing and observability

Twenty distinct `user` keys sent to the virtual model `gateway-default`
([canary_split.txt](experiments/canary_split.txt),
[metrics_snapshot.txt](experiments/metrics_snapshot.txt),
[admin_backends.json](experiments/admin_backends.json)):

| Route | Requests |
|---|---:|
| primary (qwen05) | 14 |
| canary (qwen15) | 6 |

Configured canary share 20 %, observed 30 % on 20 users — within binomial noise (P(≥ 6 of 20
at 0.2) ≈ 0.2). Routing is a SHA-256 bucket of the user key, so each user always lands on the
same variant; the split converges with the population, not per request. The Prometheus
snapshot agrees with the run: 34 direct requests to `qwen05` and 98 to `qwen15` (evaluation
plus load tests), 14 primary and 6 canary, `llmgate_breaker_open` 0 for both backends, and
the admin endpoint reports both breakers closed with zero failures.

## 5. What this project demonstrates

- A promotion decision is a **policy over paired statistics and SLOs**, not a leaderboard: a
  clearly better model was held on latency, and the exit code carries the decision into CI.
- Deterministic scorers with value checks expose small-model failure modes that a
  schema-only or vibe-based check would pass — invented acronyms, wrong currencies, a
  non-refusal.
- The serving path is part of the model's behaviour: same weights, different backend,
  different latency profile. Evaluate on the path you deploy.
